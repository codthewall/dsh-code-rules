# ADR-0001 规则文件回退采用整份快照、环形保留 3 代

- 状态：已接受（2026-11-09）
- 决策者：用户 + 主 agent
- 相关：GLOSSARY「代」「回退」「变更记录」

## 背景

用户要求："维护过程中该文件自动完善……可回退最多两个版本。"

规则文件会被 AI 持续修改（新增、细化），因此必须有回退手段。问题是怎么存历史、回退的粒度是什么。

## 选项

1. **整份快照，环形 3 代**（当前 + v-1 + v-2）。每次修改前把旧内容存为 `v-1`，`v-2` 丢弃。
2. **逐条规则的 diff 历史**。每条规则一个版本链，可单独回退某一条。
3. **依赖 git 历史**。不自己存，回退靠 `git checkout`。

## 决策

选 1。

## 理由

- 用户要的是"把文件退回到几分钟前"，不是"把某一条规则退回去"。第 2 种能做的精细回退，实际很少有人用；而且判断"这条规则当时为什么加"比判断"整份文件当时长什么样"难得多。
- 规则文件是**整体一致性**的产物（行数上限、命名风格、注释密度互相牵制），单条回退容易造成半新半旧的矛盾版本。
- 不依赖 git：用户的项目未必是 git 仓库，且回退不该要求用户会 git 命令。
- 3 代是用户明确要的"两个版本"。环形意味着回退动作本身也入历史，误回退可再退回。

## 后果

- 存储成本：3 份文件副本，可忽略。
- 丢失更早历史：接受。超过 2 代的回溯不做。
- 回退是"整份替换"，不做三方合并；回退后如需保留新版，用户应先手动复制。

## 实现注记

- 快照目录、命名、是否随项目提交，见待定的 `/rules` 存储方案。
- 快照写入必须在**修改落盘之前**完成，且写入失败时禁止修改（宁可不改，也不能丢历史）。
